# FUNC-025 修图工具与算法交付对账

状态：开发中，算法能力对账。需求关联：`feature-list.md` 中 FACE、EYE、BROW、NOSE、MOUTH、SKIN、MAKEUP、BODY、CLOTH、REPAIR 各组；实际需求编号以原目录为准。本文件不增加“已完成”的功能数量。

## 目标

参照像素蛋糕完整桌面手册梳理工具和细项，先完成实际图像效果，再开放稳定的Web控件、后端和精细MCP调用。完整公开资料、每个工具的差距和算法策略见[手册功能审计](../research/pixelcake-manual-functional-audit-20261015.md)。它描述公开功能及本项目拟用算法，不声称得知竞品私有实现。

## 每个细项必须记录的字段

1. 用户意图与部位：改变什么、正负方向、左右/上下联动、适用人物及遮挡条件。
2. 当前能力：已可执行且有视觉证据 / 可执行但效果失败 / 仅原型 / 未实现。不能以UI有同名滑杆判定已实现。
3. 算法：定位输入、目标生成、几何或颜色运算、覆盖/保护、补全、输出合成及不确定性。
4. 回放：原图、原检测、参数、引擎版本、二进制哈希与执行端；保留原图和失败结果。
5. 结果：自动合同、原尺寸比较、实际作用幅度、开销、已知失败与下一步；图像效果与工程通路分开验收。

## 前后端与 MCP 合同

本轮不新增MCP工作流。已验收的原子能力应由同一Rust操作实现供Web/WASM和Go/native使用，MCP只是带明确参数的调用入口。后续必须能表达：人物ID、部位ID、左右/上下侧、程度、保护蒙版、原图坐标、检测版本、预设与局部增量；涉及未实现结构时明确拒绝。

执行反馈应记录请求目标、受约束目标、实际移动或颜色变化及拒绝原因。多个操作先明确联合目标与坐标版本，AI不能通过重复叠加强度绕过保护，也不能把静默no-op当成功。手工路径不依赖Agent或外部账号。

## 完成标准与测试用例

- 零值精确恒等、正负方向/强度单调、强档真实生效、保护与无关部位不变、透明度正确。
- 几何类检查各部位特有的曲率/比例/接缝；颜色类检查纹理/色相/亮度；修补类检查结构和新旧材质衔接。
- 对每项保留开发原图与持出原图。检测正确与错误的案例分开记录；多档不能冒充多张独立照片。
- 原尺寸视觉不通过则不能标记质量合格，即使单测和跨端一致性通过。
- 算法通过后再做页面/API/MCP逐像素回放和错误提示验证；未验收原型不能直接进公开能力目录。
